## Decision 1 — Auth: **Better Auth** (over Supabase Auth)

| Need | Better Auth | Supabase Auth |
|---|---|---|
| Custom roles created at runtime | ✅ `organization({ dynamicAccessControl })` | ❌ build yourself (custom claims + tables) |
| Orgs / branches | ✅ organizations + `teams` built in | ❌ build yourself |
| Works with Prisma | ✅ official `prismaAdapter`, auth tables live in your Prisma schema | ⚠️ users live in `auth` schema outside Prisma |
| Main Supabase Auth advantage: RLS via `auth.uid()` | n/a | Lost anyway — Prisma connects as a privileged role and bypasses RLS |

With Prisma, RLS stops being the security boundary, so Supabase Auth's biggest advantage goes away. Better Auth already provides orgs, branches and custom roles, and your needs match exactly. Supabase stays as **Postgres + Storage** (pastry images).

**Assumption:** each bakery business is an **Organization** (tenant). Each **Branch** is a Better Auth **Team** (so branch staff membership comes for free), and domain tables reference it via `branchId`. Every domain table carries `organizationId`. The same design works for one business or many.

## Decision 2 — Backend architecture

- **Route Handlers (REST) instead of Server Actions** for data, because TanStack Query wants fetchable endpoints (caching, refetch, invalidation) and a REST API can later serve a mobile app or POS tablet.
- **Layering per feature:** `route.ts` (HTTP + auth session) → `service.ts` (business rules, permission check, transactions) → `repository.ts` (Prisma queries only). Zod schemas in `schemas.ts` are shared by the client forms and the server validation.
- **Authorization:** one `requirePermission(ctx, { product: ["create"] })` helper in `src/server/auth/` wraps Better Auth `hasPermission`. Every service call gets a `ctx = { userId, organizationId, branchId }`, and repositories always filter by `organizationId`.
- **State split:** TanStack Query = all server data. Zustand = client-only state (active branch, POS cart, UI prefs). Never mirror server data into Zustand.
- **Prisma + Supabase:** `DATABASE_URL` = pooled (port 6543, `?pgbouncer=true`), `DIRECT_URL` = direct (5432) for migrations.

## Execution notes (2026-09-29)

Where the actual scaffold run differed from the plan above:
- **Next 16.3:** `middleware.ts` is deprecated; use `src/proxy.ts`. `create-next-app` also generated `AGENTS.md`, which `CLAUDE.md` imports via `@AGENTS.md`.
- **`@types/node` bumped to ^24:** Vitest 5 refused the `^20` that create-next-app pinned. ^24 matches the local Node v24.
- **Prisma 7:** config lives in `prisma.config.ts` (renamed from the generated `prisma7.config.ts`). The CLI uses `DIRECT_URL`; the app must use `@prisma/adapter-pg` with the pooled `DATABASE_URL`. The client is generated to `src/generated/prisma` (gitignored), so run `npm run db:generate` after install. Added deps: `@prisma/adapter-pg`, `pg`, `@types/pg`, `dotenv`.
- `prisma init` installed Prisma agent skills. We kept them in `.claude/skills/` and removed the `.agents/` and `.windsurf/` copies.
- `npm audit` reports 4 high findings inside the Prisma 7 CLI's own deps (`mysql2`, `deepmerge-ts`). They are dev-only, and the only fix npm offers is downgrading to Prisma 6, so we left them.
- `.gitignore` ignores `.env*` except `.env.example`. `db:seed` runs `prisma db seed`, and the seed command is set in `prisma.config.ts`.
